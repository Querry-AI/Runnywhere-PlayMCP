# 출발지 발화 분류와 구 단위 코스 추천 구현 설계도

작성일: 2026-08-28
개정: 2026-08-28 (3차 — 서울 전역 추천 제거, 구 단위 추천 도입)
대상 저장소: Runnywhere
범위: 출발지 발화 분류, 구 단위 추천, 조건 검증, 편집 안내, 실패 분류, Preview 배포 검증

## 확정된 결정 4건

이 개정판은 다음 네 결정 위에 서 있다. 나머지 절은 전부 이 결정의 귀결이다.

1. **출발지가 없는 코스 생성 요청은 답변으로 출발지를 요구한다.** 거리·모양·야간 같은 조건이 있어도 마찬가지다.
2. **`"서울 시내"`, `"아무데나"` 같은 서울 전역 범위도 출발지로 인정하지 않는다.** 되묻는다.
3. **구 단위(`"강남구"`)는 유효한 출발 범위로 지원한다.** 이것이 1·2의 질문에 대한 가장 흔한 답이기 때문이다.
4. **대화로 코스를 수정하는 경로는 본선 범위에서 제거한다.** 대신 모든 답변이 코스를 편집할 수 있다는 사실을 눈에 보이게 알린다.

결정 1·2는 지연 실측이 지지하지 않는다. 아래 "지연 실측"이 그 대가를 숫자로 남긴다.
채택 이유는 지연이 아니라 관련성이다. 서버가 고른 임의의 역이 사용자가 실제로 갈 수 있는
곳이라는 보장이 없고, `"7km 코스 짜줘"`라고 말한 사람은 `"어디든 좋다"`고 말한 적이 없다.

## 현재 배포 판정

배포 보류. 숫자 점수는 사용하지 않는다. 차단 근거는 다음 여섯 가지다.

- **일정이 가장 강한 제약이다.** 오늘은 8월 28일이고 본선용 개발 완료는 8월 31일이다. 9월 1일부터 9월 11일은 카카오 QA와 오류 수정 구간이고 9월 14일에 코드가 프리징된다. 남은 개발 가능 기간은 3일이다.
- 로컬 구현이 출발지 없는 요청에 임의의 역을 만들어 넣는다.
- `resolve_location()`이 범위 표현을 막지 않아 `"서울 시내"`가 압구정의 상호명으로 해석된다.
- 구 단위 요청이 `"강남구"`를 빼면 전부 `location_not_found`다.
- Preview에 적용된 `create_seoul_running_course` 설명은 로컬 변경 전 계약이다.
- 코스를 만들지 못한 실패가 전부 `invalid_request`로 나가 모델에게 입력을 고치라고 지시한다.

Kakao 개발가이드의 직접 제약은 툴 설명 1,024자 이하, 평균 응답 100ms 이내와 p99 3,000ms,
Preview 실제 발화 검증이다. 본선 가이드상 8월 31일 이후에는 오류 위주 수정만 가능하므로,
**측정과 검증이 끝나지 않은 작업은 미루는 것이 아니라 본선 범위에서 제외하는 것**으로 처리한다.

## 지연 실측

Kakao 개발가이드 5.1.a: "툴의 응답속도는 평균 100ms 이내, p99 3,000ms 필수".

`offloaded()`가 `MCP_OUTER_RESPONSE_BUDGET_S = 2.85`초에서 요청을 자르고 `generation_timeout`을
반환한다. 이 상한은 MCP 경로에서만 적용되며, 동기 함수를 직접 호출하는 벤치는 우회한다.
아래 표는 2.85초를 넘긴 표본 수를 따로 센다.

### 무출발지 경로 (30회씩, 웜 상태)

| 경로 | 평균 | p99 | 실패 |
|---|---|---|---|
| 동물 + 거리 (whale 7km) | 8ms | 9ms | 0/30 |
| 동물 거리 미지정 (best_animal) | 9ms | 11ms | 0/30 |
| 공원 (무출발지) | 4ms | 4ms | 0/30 |
| 일반 + 거리 (5km) | 239ms | 1,258ms | 1/30 |
| 일반 + 야간 | 434ms | 2,050ms | 4/30 |

### 출발지 풀 비교 (n=60, 전략마다 캐시 초기화)

| 풀 | 평균 | p50 | p99 | 2.85s 초과 | 실패 |
|---|---|---|---|---|---|
| 검증 프리셋 역 (서울 전역 추천이 쓰던 풀) | 356ms | 231ms | **1,975ms** | 0/60 | 0/60 |
| 전체 역 + 재시도 (사용자가 답할 법한 위치) | 555ms | 328ms | **2,996ms** | **1/60** | 0/60 |
| 구 무작위 역 | 544ms | 334ms | 2,532ms | 0/60 | 0/60 |
| 구 무작위 역 + 같은 구 재시도 | 600ms | 362ms | 2,343ms | 0/60 | 0/60 |
| 동물 · 구 프리셋 직배송 | **7ms** | 7ms | 13ms | 0/60 | 0/60 |

### 결정 1·2의 대가

- **p99가 나빠진다.** 서울 전역 추천은 코스가 잘 만들어지는 것이 검증된 프리셋 역에서만
  출발점을 골랐다(p99 1,975ms, 초과 0/60). 사용자가 말하는 임의의 위치는 그 검증을 거치지
  않는다(p99 2,996ms, 초과 1/60). 상한을 넘겨 `generation_timeout`으로 죽는 호출이 생긴다.
- **동물 코스가 8ms에서 59ms로 느려진다.** 8ms는 프리셋을 그대로 내보내던 값이다.
- **야간 구제책을 잃는다.** 강남역 야간은 30/30 실패하는데 서울 전역 추천은 조명이 확인된
  역을 골라 26/30 성공했다. 이제 그 구제는 §4의 구 단위 안내가 대신한다.
- **개선되는 것은 평균 하나뿐이고 공짜가 아니다.** `missing_start`는 생성이 없어 약 0ms이므로
  이 응답이 늘면 평균이 내려간다. 그러나 그것은 답을 못 하는 호출을 늘려 얻는 값이고, 본선
  가이드 3.c("툴 호출이 잘 되도록 Tool Description을 잘 정의하는 것도 심사 기준")와 반대 방향이다.
- **구 단위는 안정적이다.** p99 2,532ms, 2.85초 초과 0/60, 실패 0/60. 결정 3이 결정 1·2의
  대가를 실제로 상쇄하는 지점이 여기다.

일반 코스가 평균 100ms를 넘는 것은 어느 경로든 동일한 생성 비용이며, 이번 변경이 만든 비용이 아니다.

## 핵심 설계

새로운 거대한 의도 분석 계층은 만들지 않는다. 서버 입구에서 네 상태만 구분한다.

```text
사용자 발화
  └─ create_seoul_running_course 1회
       ├─ missing   → 출발지 없음. 서울 전역 범위 표현 포함. 위치 질문(missing_start)
       ├─ district  → 서울 25개 구 중 하나. 그 구의 후보에서 선정
       └─ specific  → 기존 Kakao/오프라인 지오코딩 → 그 지점에서 코스 생성
          (invalid_coordinates → 좌표가 하나만 온 경우)
```

판정 우선순위:

1. `lat`, `lon` 모두 존재: `specific`
2. 둘 중 하나만 존재: `invalid_coordinates`
3. `need_facilities`에 `park`가 있고 출발지가 없음: 공원 카탈로그 경로 (아래 예외)
4. `location`과 좌표가 모두 없음: **조건 유무와 무관하게** `missing`
5. 정규화된 `location`이 서울 전역 범위 표현: `missing`
6. 정규화된 `location`이 서울 25개 구 중 하나: `district`
7. 나머지: `specific`

`"7km 고래 코스 짜줘"`도, `"서울 시내에서 7km 고래 코스"`도 `missing`이다. 거리나 모양은
어디서 출발할지를 말해 주지 않고, 서울 전역은 출발지가 아니라 서비스의 전체 범위다.

**공원 요청은 예외다.** `need_facilities=["park"]`는 달릴 장소를 이미 지정한 것이고 등록된
5곳이 그 자체로 목적지다. 예선부터 동작하던 무출발지 공원 추천을 유지한다. 이 예외를
없애려면 판정 규칙 3을 지우면 된다.

코스 유형별 최초 배포 범위:

- 동물: `district`와 `specific`에서 기존 검증 프리셋으로 선정. **단 야간은 제외**(§5)
- 공원·수변: 기존 5개 등록 코스. 무출발지 허용
- 일반 코스: `district`와 `specific`에서 생성

추가하지 않는 것: 신규 DB, 세션, 외부 의도분석 API, 런타임 서울 전역 그래프 탐색,
서울 전역 후보 카탈로그, `selection_mode` 필드.

## 1. 출발지가 없으면 출발지를 요구한다

현재 `src/runart/server.py`의 `_has_named_start()`는 출발지 없음과 서울 전역 표현을 모두
`False`로 반환하고 `_random_seoul_start()`로 임의의 역을 채운다. 이 자동 대체가 첫 번째
수정 대상이다.

### 구현

`_has_named_start()`와 `_random_seoul_start()`를 삭제하고 다음으로 바꾼다.

```python
StartScope = Literal["missing", "district", "specific", "invalid_coordinates"]

def _classify_start_scope(request: dict) -> StartScope:
    ...
```

`create_seoul_running_course()` 분기 순서:

```python
if "park" in (need_facilities or []):
    return _park_course_result(common, course_type)

scope = _classify_start_scope(common)

if scope == "invalid_coordinates":
    return invalid_coordinates_result()

if scope == "missing":
    return missing_start_result()

if scope == "district":
    return select_district_courses(...)

return generate_from_specific_start(...)
```

중요한 계약:

- 서버는 출발지가 없는 요청에 임의의 역을 만들어 넣지 않는다.
- 거리·모양·야간 같은 조건은 출발지를 대신하지 못한다.
- `"서울 시내"`, `"서울 전역"`, `"아무데나"`는 출발지가 아니다. `missing`으로 되묻는다.
- `"강남구"`처럼 구를 말한 요청은 `district`다.
- 공원 요청은 달릴 장소를 이미 말한 것이므로 무출발지에서도 추천한다.

### `missing_start` 응답

질문만 던지지 않고 **어떻게 답하면 되는지 함께 보여준다.** 사용자가 다음 턴에 무엇을 말해야
할지 모르면 대화가 한 번 더 왕복한다. 결정 1·2가 만든 왕복 비용을 한 번으로 끝내는 것이
이 문구의 역할이다.

```text
어디에서 출발할지 알려주세요.
구 이름(강남구), 역 이름(성수역), 가게 이름, 도로명·지번 주소 모두 좋아요.
```

- `is_error=True`, `result_code="missing_start"`, 위젯 없음
- 개발가이드 2.4.c에 따라 위젯이 아닌 정제된 마크다운 텍스트로 반환
- **구 이름을 첫 예시로 둔다.** 가장 답하기 쉽고, §4가 실제로 처리한다
- 서울 전역 표현으로 되물린 경우에는 그 사실을 한 줄 덧붙인다

```text
서울 전체에서 고르기보다 조금 좁혀 주시면 실제로 갈 수 있는 코스를 찾아드릴 수 있어요.
구 이름만 알려주셔도 충분해요.
```

### 유지되는 기존 동작

무출발지 공원 추천은 그대로 보존한다. `test_legacy_park_calls_also_return_one_three_destination_widget`을
포함한 기존 무출발지 공원 테스트는 **교체하지 않고 유지**한다.

### 테스트

`tests/test_citywide_start.py`를 표 기반으로 확장한다.

- `location=None` + 조건 없음 → `missing`
- `location=None` + `distance_km=7` → `missing` (조건은 출발지를 대신하지 못한다)
- `location=None` + `course_type="whale"` → `missing`
- `""`, `"   "` → `missing`
- `"서울 시내"`, `"서울 전역"`, `"서울시 아무데나"`, `"아무데나"`, `"어디든"` → `missing`
- `location=None` + `need_facilities=["park"]` → 공원 카탈로그 3곳 (예외)
- `"강남구"`, `"마포구"`, `"서울 성동구"` → `district`
- `"강남역"`, `"서울시청"`, `"서울 성동구 아차산로 100"` → `specific`
- 위도만 전달 → `invalid_coordinates`
- `missing_start`는 위젯이 없고 안내 첫 예시가 구 이름이다
- `missing`·`district` 요청은 지오코더를 호출하지 않는다

## 2. 운영 툴 설명과 서버 전체 지침 통합

현재 FastMCP 지침과 툴 필드 설명이 서로 충돌하고, Preview에 적용된 설명은 이전 계약이다.

### 수정 대상

- `FastMCP(... instructions=...)`
- `create_seoul_running_course()` docstring
- `location`의 `Field(description=...)`
- `include_hills`, `need_facilities`의 필드 설명
- `_legacy_generate_running_course`, `_legacy_generate_animal_course` 브리지

### description 예산

현재 등록된 `create_seoul_running_course` description은 서비스명 suffix 포함 1,021자다.
Kakao 가이드 상한 1,024자에 3자만 남는다.

이번 개정으로 예산이 크게 회수된다.

- 결정 4로 후속 참조 유도 문장이 사라진다
- 서울 전역 추천이 사라져 `random`/`best_match` 설명이 통째로 빠진다
- `selection_mode` 필드를 추가하지 않는다

목표는 서비스명 suffix 포함 900자 이하다.

**`FastMCP.instructions`로 지시를 옮기지 않는다.** 카카오가 MCP `initialize` 응답의 서버
instructions를 모델 컨텍스트에 전달한다는 근거가 두 가이드 어디에도 없다. 개발가이드 2.2가
필수로 요구하는 것은 툴 단위의 `name`, `description`, `inputSchema`, `annotations`뿐이다.
호출 라우팅에 필요한 규칙은 전부 툴 description 안에 남긴다.

### 새 발화 계약

- 사용자가 구체적인 출발지를 말했다면 원문 그대로 `location`에 전달
- 사용자가 구를 말했다면 그 구 이름을 `location`에 전달
- 출발지를 말하지 않았으면 **`location`을 비운 채 호출**한다. 서버가 되묻는다
- `"서울 시내"`, `"아무데나"` 같은 표현도 지어내지 말고 그대로 전달한다. 서버가 되묻는다
- 코스 추천은 `create_seoul_running_course`를 정확히 한 번만 호출

`LOCATION_FIELD_EN`은 `refine_course()`에서도 재사용하므로 분리한다.

- 신규 코스용: 특정 출발지와 구 이름을 모두 설명
- 코스 수정용: 특정 새 출발지만 허용

### 레거시 Preview 브리지

Preview가 이전 8툴 스키마를 캐시한 동안 `generate_running_course`와 `generate_animal_course`도
계속 호출될 수 있다. 두 브리지에서 별도 범위 로직을 복제하지 않는다.

```python
def _dispatch_course_request(course_type: str, request: dict) -> CallToolResult:
    # missing / district / specific을 한 번만 판정
    ...
```

통합 툴과 두 레거시 브리지가 이 함수를 함께 사용한다. 레거시 호출도 최신 정책을 따른다.

### annotations

생성 툴 3개(`create_seoul_running_course`와 두 레거시 브리지)의 응답은 더 이상 무작위가
아니다. 같은 출발지와 조건이면 같은 코스가 나온다. 따라서 `idempotentHint=True`를 유지한다.

`_RO`를 분리할 필요가 없어졌다. 개발가이드 2.2.b는 다섯 항목의 값을 모두 지정하라고만
요구하며 특정 값을 강제하지 않는다.

### 테스트

- 세 설명 표면에 `missing / district / specific` 계약이 모두 존재
- 출발지가 없으면 `location`을 비우고 호출하라는 문장이 존재
- 임의 위치를 만들어 넣으라는 문장은 없어야 함
- 특정 주소·상호명은 그대로 전달하라는 기존 계약 유지
- 등록된 통합 툴 description 길이 `<= 900`
- 모든 툴 description 길이 `<= 1024`
- 통합 툴과 두 레거시 툴에 같은 범위 분류 테스트 적용

## 3. 범위 표현은 지오코딩하지 않고 되묻는다

Preview에서 `"서울 시내"`가 압구정의 특정 상호명으로 변환된 것은 Kakao API 장애가 아니라
범위 문장이 키워드 지오코더에 들어간 의미 오류다. 결정 2로 서울 전역을 추천하지 않게 됐지만,
**차단은 여전히 필요하다.** 막지 않으면 `"서울 시내"`가 임의의 상호명으로 해석되어 사용자가
말한 적 없는 출발지에서 코스가 나온다.

### 개발가이드와의 관계

개발가이드 5.3.a.i는 "description을 이용하여 LLM에게 사용자의 프롬프트를 파라미터로 받는
것"을 금지한다. `location`은 출발지 슬롯이므로 그 자체로는 위반이 아니다. 이번 개정은 문장형
범위 표현을 받아 처리하지 않고 되묻는 방향이므로 이 경계에서 더 멀어진다.

### 구현 위치

공통 방어 로직은 `src/runart/geocode.py`에 둔다.

```python
def is_citywide_scope(text: str | None) -> bool:
    ...

def resolve_location(...):
    if is_citywide_scope(location):
        raise CourseError("어디에서 출발할지 조금 더 좁혀서 알려주세요. 구 이름만 알려주셔도 충분해요.")
```

`server._classify_start_scope()`도 같은 `is_citywide_scope()`를 사용한다. 서버와 지오코더가
각자 다른 목록을 갖지 않게 하는 것이 핵심이다.

### 표현 정규화

표준 라이브러리 `re`만 사용한다.

- 공백, 쉼표, 마침표 제거
- 조사·문장 꼬리 일부 허용
- 전체 문장 기준으로만 매칭
- 특정 장소나 구 이름이 섞이면 서울 전역으로 판정하지 않는다

**`서울` 접두가 없는 범위 표현도 포함한다.** 이 서비스는 서울 안에서만 코스를 만들므로
`"아무데나"`는 `"서울 아무데나"`와 같은 뜻이고 모호하지 않다. 접두를 요구하면 그 표현들이
곧장 지오코더로 들어가 압구정 사고를 재현한다.

되묻을 표현:

- 서울 / 서울시 / 서울특별시
- 서울 전역 / 서울 시내 / 서울시 아무데나 / 서울 어디서든
- 서울 안의 모든 코스 중에서
- 아무데나 / 아무 곳이나 / 어디든 / 어디든지 / 어디나
- 랜덤 / 랜덤으로 / 상관없음 / 아무거나

되물으면 안 되는 표현:

- 서울역 / 서울시청 / 서울숲 / 서울대입구역
- **강남구 / 서울 강남구** — `district`다
- 서울시 마포구 상암동 1601 — 주소다

### 테스트

- 서울 전역 문장을 `resolve_location()`에 직접 전달하면 Kakao 호출 전 실패
- `"서울역"`, `"서울시청"`은 정상 지오코딩
- `"아무데나"`, `"어디든"`이 `specific`으로 새지 않음
- **`"강남구"`가 서울 전역으로 오판되지 않음**
- `refine_course(location="서울 시내")`는 잘못된 상호명으로 이동하지 않고 명시적 오류

## 4. `district` — 구 단위 요청

`"강남구"`처럼 구를 말한 요청은 지금 대부분 깨진다. 실측:

| 요청 | 현재 결과 |
|---|---|
| `강남구` | 강남역으로 해석 — GAZETTEER fuzzy가 `"강남"`을 `"강남구"` 안에서 찾은 **우연** |
| `마포구` | `location_not_found` |
| `성동구` | `location_not_found` |
| `송파구` | `location_not_found` |
| `종로구` | `location_not_found` |

(로컬에 Kakao API 키가 없어 오프라인 경로만 측정했다. 운영에서는 키워드 검색이 `"마포구"`를
마포구청 같은 POI로 해석할 수 있으나 그것은 설계가 아니라 우연이고, 구청은 구의 대표점이 아니다.)

**이 절은 결정 1·2를 성립시키는 절이다.** `"어디에서 출발할까요"`에 사용자가 가장 흔하게
답하는 단위가 구인데 그것이 깨지면 되묻는 정책 자체가 성립하지 않는다.

### 데이터는 이미 있다

새 파일도 ETL도 필요 없다.

| 소스 | 구 커버리지 |
|---|---|
| `SEOUL_METRO_STATIONS` 289개 | 주소 문자열로 274개에서 구 판별 → **25/25 구** |
| `_SEOUL_DISTRICTS` (geocode.py:38) | 25개 구 튜플이 이미 존재 |
| 검증 동물 프리셋 339개 | **25/25 구** (최소 용산구 2 · 금천구 2) |
| 야간 조명 통과 프리셋 28개 | **16/25 구** — 9개 구는 0개 |

### 구현

- `geocode.py`에 `district_of(text)`를 두어 `_SEOUL_DISTRICTS`로 구를 판별한다.
  서버와 지오코더가 각자 다른 목록을 갖지 않게 하는 것은 §3과 같은 원칙이다.
- 역 주소 문자열에서 구를 뽑아 구별 역 목록을 만든다. 빌드 타임 데이터가 아니라 기동 시
  1회 파생으로 충분하다(289행 스캔).
- 동물·공원: 기존 후보원을 구로 필터링한 뒤 §5의 조건 필터와 순위 선정을 그대로 적용한다.
- 일반 코스: 그 구의 역 중 하나를 골라 생성한다.
- `"강남구"`가 지오코더로 새지 않도록 `district` 판정이 `resolve_location()` 호출보다 앞선다.
- 같은 역에 여러 검증 경로가 있고 한 역의 여러 노선이 서로 다른 좌표를 가지므로,
  `location_name`으로도 중복을 제거한다.

### 지연

§ "지연 실측"의 표대로 동물 7ms, 일반 544ms, p99 2,532ms, 2.85초 초과 0/60, 실패 0/60이다.

**재시도는 붙이지 않는다.** 실패가 이미 0인데 평균만 544ms에서 600ms로 늘어난다.

### 야간의 구멍

야간 조명 통과 프리셋이 있는 구는 16/25다. 나머지 9개 구의 야간 요청은 그 구 안에서 조명
기준을 통과하는 코스를 찾지 못할 수 있다. 어두운 코스로 채우지 않고 §7의 안내로 넘긴다.
서울 전역 추천이 사라졌으므로 안내는 **다른 구**를 가리킨다.

```text
강북구에서는 조명이 확인된 야간 코스를 찾지 못했어요.
성북구, 영등포구, 양천구 쪽에는 조명이 확인된 코스가 있어요.
```

제시할 구는 조명 통과 프리셋 보유 수 상위에서 고른다(성북 4 · 영등포 4 · 양천 3 · 중랑 3).

### 테스트

- 25개 구 이름이 모두 `district`로 분류된다
- `"서울 강남구"`, `"강남구 근처"`도 `district`
- `"서울 성동구 아차산로 100"`은 `specific` (구가 들어 있어도 주소는 주소다)
- `district` 요청이 `resolve_location()`을 호출하지 않는다
- 반환된 코스의 출발지가 요청한 구 안에 있다
- 야간 미커버 9개 구는 `insufficient_courses`와 다른 구 안내를 반환한다

## 5. 명시 조건은 필수 필터로 처리

현재 `facility_requirement_score()`와 `courseplan.py`는 시설을 선호도 점수로만 사용한다.
`district`는 후보가 여럿이므로 명시 조건을 필수 필터로 처리한다.

### 입력 계약 수정

```python
include_hills: bool | None = None
```

- `None`: 지형 언급 없음
- `False`: 명시적인 평지 요청
- `True`: 명시적인 언덕·업힐 요청

기존 `CourseParams`의 기본 `False`는 과거 `course_id` 호환성을 위해 유지한다. `specific`
생성 경로에서는 `None`을 기존 기본값 `False`로 정규화하고, `district` 후보 필터에서만
삼상태 의미를 사용한다.

**캐시된 스키마 대응이 필수다.** 현재 필드 설명은 "평지 또는 언급이 없으면 false"이므로,
지형을 말하지 않은 요청도 모델이 `False`를 보낸다. 툴 재등록 전의 Preview와 삼상태가 없는
레거시 브리지는 계속 그렇게 보낸다. 이 값을 그대로 "명시적 평지 요청"으로 승격하면 모든
`district` 요청이 평지 전용이 된다.

- 레거시 브리지 호출: `include_hills=False`를 `None`으로 매핑한다
- 통합 툴 호출: 재등록된 새 스키마의 삼상태를 그대로 사용한다
- 이 매핑 규칙을 테스트로 고정한다

시설 필드는 문자열 배열 대신 항목 enum을 노출한다.

```python
list[Literal["convenience_store", "restroom", "water", "park"]] | None
```

### 필수 조건

| 조건 | 통과 기준 |
|---|---|
| 거리 | 실제 거리 오차 ±10% |
| 야간 | 측정 조명 점수 `>= 0.4` |
| 평지 | `course.is_flat is True` |
| 언덕 | `course.is_flat is False` |
| 시설 | 요청한 모든 시설 종류가 코스 10m 반경에 존재 |
| 특정 동물 | 실제 `params.shape`가 요청 모양과 동일 |
| 일반 코스 | 동물 모양이 없는 코스 |

필터 이후:

- 3개 이상: 상위 3개
- 1~2개: 있는 만큼만 반환
- 0개: 위젯 없이 `insufficient_courses`
- 조건을 어긴 대체 코스를 성공 카드로 반환하지 않음

개발가이드 2.4.c는 "tool call result가 error인 경우와 widget json이 아닌 경우에는 text
content에 정제된 텍스트 형식(마크다운)을 권장"하고, 본선 가이드는 "툴 호출에 위젯 답변은
필수가 아닌 권장"이라고 명시한다. 조건 미충족 응답을 위젯 없이 마크다운으로 내는 것은
가이드와 정합한다.

### 시설 필터 비용

측정했다. 고래 프리셋 107개에 `restroom` 필터가 0.15초, 두 종류가 0.14초다. 구로 좁히면
후보가 더 줄어든다. 사전 계산된 비트셋 없이 최초 배포에서 동작한다.

### 야간 후보 선정

야간은 코스를 만든 뒤에만 거르는 후처리로 두지 않는다.

- `district` 일반: 그 구 안에서 조명 기준을 통과한 프리셋이 있는 역을 출발 후보로 우선 사용
- 생성 후에도 그 코스 자체의 조명을 다시 하드 필터
- 공원: 기존 공원 프리셋 중 같은 기준을 통과한 코스만 포함 (5개 중 4개 통과)
- 기준을 넘는 코스가 없으면 어두운 코스로 채우지 않고 `insufficient_courses`

### 야간 동물은 최초 배포에서 제외한다

동물 프리셋을 야간 파라미터로 재사용하면 **공유된 링크가 죽는다.** 실증했다.

```
조명 통과 고래 프리셋(서울역, 10.97km)을 night_mode=True로 인코딩한 뒤 캐시를 비우고 복원
→ CourseError: 고래 옆모습 실루엣이 충분히 또렷하지 않아 추천하지 않을게요
```

원인은 `animal_presets.get_animal_preset()`이 `night_mode`, `include_hills`, `need_facilities`
중 하나라도 설정되면 프리셋을 무시하고 `MISSING`을 반환하기 때문이다. 동물 프리셋은 공원
프리셋과 달리 `params.manual_path`에 경로를 담지 않으므로 복원 시 재생성된다.

| 안 | 판정 |
|---|---|
| (a) 동물 프리셋도 `manual_path`를 `course_id`에 싣기 | **불가.** `course_id`가 186자 → **1,562자**. 공원이 348~488자로 끝나는 것은 경로가 29~59노드이기 때문이고 동물은 중앙값 169노드다. 위젯 12,000바이트 상한을 위협한다 |
| (b) `get_animal_preset`의 `night_mode` 가드 해제 | **부작용 있음.** 이미 공유된 야간 동물 링크의 경로가 조용히 달라진다 |
| (c) 야간 동물을 최초 배포에서 제외 | **채택.** 후보 풀이 원래 얇다 |

조명 실측 통과 프리셋은 339개 중 28개다(cat 2 / dog 9 / rabbit 4 / whale 13). 거리 ±10%까지
걸면 `"강남구 야간 7km 고양이"`의 후보는 사실상 0이다. 야간 동물 요청은 기존 생성 경로로
답하고, 만들 수 없으면 `insufficient_courses`를 반환한다.

### 응답의 조건 보고

```json
{
  "conditions_requested": {"distance_km": 7, "terrain": "flat", "facilities": ["restroom"]},
  "conditions_satisfied": true,
  "unmet_conditions": []
}
```

후보가 없을 때는 조건별 탈락 수를 제공한다.

```json
{
  "unmet_conditions": ["restroom"],
  "rejection_counts": {"distance": 41, "terrain": 12, "restroom": 85}
}
```

이를 통해 모델이 모든 조건을 적용했다고 잘못 요약하는 것을 막는다. 개발가이드 2.4.b의
"result의 크기는 최소한으로"에 맞춰 문자열 배열이 아니라 정수 카운트로 유지한다.

## 6. 대화 수정 경로 제거와 편집 안내 노출

추천 토큰은 구현하지 않는다. 대화로 코스를 수정하는 경로 자체를 본선 범위에서 제거한다.

### 근거

개발가이드 3.1.a:

- 위젯 사용 시: "ChatGPT for Kakao는 제공자가 구성한 위젯의 내용을 그대로 답변으로 사용합니다. 따라서 LLM이 답변을 가공하지 않습니다."
- 위젯 미사용 시: "제공자의 답변 텍스트(Markdown)를 활용하여 맥락에 적합한 답변을 생성합니다."

즉 위젯을 쓰는 턴에는 모델이 답변을 생성하지 않으므로, 다음 턴 컨텍스트에 `course_id`가
텍스트로 남지 않을 수 있다. 같은 응답 payload에 추천 토큰을 하나 더 넣어도 함께 유실된다.

본선 가이드 유의사항 2.b는 "개발 과정에서의 문제 해결은 도움을 드리고 있지 않습니다(기능
오류, 코드 오류, 버그, 위젯 UI 구성 오류)"라고 명시하므로, 카카오에 문의해 답을 받는 경로도 없다.

위젯 품질을 지키고 코스 수정은 이미 구현된 웹 편집기로 보낸다.

### 제거

- 추천 토큰(`encode_recommendation_token` / `decode_recommendation_token`) 구현하지 않음
- `recommendation_token`, `course_index` 파라미터 추가하지 않음
- 검증 매트릭스의 후속 수정·시설 조회 발화 삭제

### 유지

`refine_course`와 `find_facilities_near_course`는 툴로 남긴다. 올바른 `course_id`를 직접
받으면 정상 동작하고 그 계약은 바뀌지 않는다. 다만 두 툴의 description에서 "이전 추천을
참조하라"는 유도를 제거하고, 회수된 글자수는 §2의 900자 목표에 쓴다.

### 편집 안내를 눈에 보이게 한다

모든 코스 응답의 가장 아래 마크다운 텍스트에 코스를 편집할 수 있다는 사실을 알린다.

현재 `COURSE_EDIT_NOTICE`는 두 곳에만 있다.

- `src/runart/widget.py`의 `copy_text` — 카카오톡 공유하기용이며 화면에 표시되지 않는다
- `assistant_final_text` — 위젯을 쓰면 LLM이 답변을 가공하지 않으므로 표시되지 않을 수 있다

따라서 **위젯 `children`의 마지막에 Text 자식으로 추가**해야 사용자 눈에 들어온다.

문구도 바꾼다. 현재 `"러닝 코스는 직접 수정할 수 있어요."`는 대화로 고칠 수 있다고 읽힌다.

```text
코스를 열면 경로를 직접 편집할 수 있어요.
```

동기화할 지점은 네 곳이다. 하나라도 빠지면 채널마다 다른 안내가 나간다.

- `src/runart/widget.py` `build_course_widget()`의 `children` 마지막 (신규)
- `src/runart/widget.py` `copy_text`
- `src/runart/server.py` `_plan_final_text()`와 `_plan_result()`의 마크다운 폴백
- `src/runart/render.py` `course_markdown()`

### 테스트

- 위젯 JSON의 마지막 자식이 편집 안내 Text임을 확인
- 네 경로가 같은 문구를 사용
- 공원 카탈로그 응답과 동물 응답 모두에 존재
- 안내 추가 후에도 위젯이 12,000바이트 상한 안에 있음
- 코스가 없는 응답(`missing_start`, `insufficient_courses`)에는 붙지 않음

## 7. 실패 분류 교정

`_course_tool_result()`의 `⚠️` 분기가 catch-all `invalid_request`다. 실측하면 서로 다른 네
원인이 하나의 코드로 나간다.

| 실패 | 현재 코드 | 맞는 코드 |
|---|---|---|
| 야간 조명 부족 (강남역) | `invalid_request` | `insufficient_courses` |
| 순환 코스 불가 (여의도) | `invalid_request` | `insufficient_courses` |
| 거리 미스 (목동) | `invalid_request` | `insufficient_courses` |
| 거리 범위 초과 (100km) | `invalid_request` | 맞음 |
| 위치 못 찾음 | `location_not_found` | 맞음 |

이는 CLAUDE.md의 불변식 위반이다.

> 툴은 예외를 던지지 않는다. 모든 실패는 다음 행동을 알려주는 한국어 안내 문자열로 반환한다.
> 실패 원인마다 다른 문구를 쓴다 — 하나의 포괄 메시지는 원인을 감춘다.

문구는 원인별로 다른데 `result_code`는 뭉개져 있다. `invalid_request`는 모델에게 "입력을
고쳐 다시 호출하라"는 신호인데 `강남역 + 야간`은 완벽히 유효한 요청이다.
`_recommendation_shortage()`가 정확히 이 상황을 위해 `repeat_tool_call=False`와
`retryable=False`를 세팅하는데 이 경로에서는 호출되지 않는다. 실측 응답의 `repeat_tool_call`이
`None`인 것이 그 증거다.

### 죽은 분기

```python
if request.get("night_mode") and not text.startswith(("⚠️", "⏱️")):
    return _recommendation_shortage(0, night_mode=True)
```

야간 실패는 항상 `⚠️`로 시작하므로 이 조건은 절대 참이 되지 않는다.

### 구현

`⚠️` 분기의 기본값을 뒤집는다. `invalid_request`는 명시적 화이트리스트로만 남긴다.

- `"위치를 찾지 못"` / `"출발 위치가 필요"` → `location_not_found` (기존 유지)
- `"추천 거리"` → `exact_shape_unavailable` (기존 유지)
- 거리·시간 범위 안내 → `invalid_request`
- 그 외 코스 부재 → `insufficient_courses` (`repeat_tool_call=False`, `retryable=False`)

죽은 야간 분기는 제거한다. 위 매핑이 그 역할을 대신한다.

기존 테스트가 `invalid_request`를 단언하는 곳은 없다(`grep` 결과 0건). 코드 내 다른 사용처는
`_park_course_result()`의 거리·시간 범위 검사 한 곳이고 그것은 진짜 `invalid_request`다.

### 실패 안내 문구

현재 야간 실패는 `"조명 정보가 부족한 길을 야간 코스로 추천하지 않아요."`로 끝나고 다음
행동이 없다. 서울 전역 추천이 사라졌으므로 안내는 **다른 구**를 가리킨다.

```text
이 출발지에서는 조명이 확인된 야간 코스를 찾지 못했어요.
성북구, 영등포구, 양천구 쪽에는 조명이 확인된 코스가 있어요.
```

**근처 지점 이동 제안을 새로 만들지 않는다.** 조명 실측을 통과한 역이 서울 전체에 23곳뿐이고
실패 지점에서 0.9~2.5km 떨어져 있어 동물 경로가 쓰는 2km 반경보다 넓다. 구를 제시하는 편이
사용자가 판단하기 쉽다.

### 야간 임계값은 낮추지 않는다

대표 16곳의 야간 5km 요청을 측정했다. 10곳 통과, 6곳 실패다.

- 조명 탈락 4곳: 강남역 0.32 · 신촌 0.34 · 상암 0.32 · 마곡 0.32 (임계값 0.4)
- 순환 코스 불가 1곳: 여의도 (주간도 실패하므로 별개 사안)
- 거리 미스 1곳: 목동 (최근접 4.2km)

CLAUDE.md에 조명은 도시 전체가 무데이터 기본값 0.5 아래라고 기록돼 있고 0.4는 이미 완화된
값이다(커밋 6dc5b09). 더 낮추면 "야간 조명 많음" 라벨이 의미를 잃는다. 실패는 데이터가
말하는 사실이므로 판정을 바꾸지 않고 **전달 방식만** 고친다.

여의도 주간 순환 코스 실패는 이 절의 범위가 아니다. `insufficient_courses`로 정직하게
보고하는 것까지만 한다.

### 테스트

- 다섯 실패가 각각 서로 다른 `result_code`를 받는다
- 코스 부재 실패는 `repeat_tool_call=False`, `retryable=False`
- 거리·시간 범위 초과만 `invalid_request`
- 야간 실패 안내에 다른 구 제안이 포함된다
- 죽은 야간 분기가 제거되어도 야간 실패가 `insufficient_courses`로 나간다

## 9. 추천 슬롯 채우기와 병렬 생성

### 무엇이 느린지 먼저 측정했다

임의 역 60곳에서 일반 5km 요청을 프로파일했다.

| 구간 | 평균 | p50 | p95 | p99 |
|---|---|---|---|---|
| 코스 1개 생성 | **61ms** | 44ms | 195ms | **328ms** |
| 툴 호출 전체 (최대 3개) | 277ms | 213ms | 826ms | 1,395ms |
| 차이 = 추가 2개 비용 | 217ms | 146ms | 718ms | 1,067ms |

**생성 자체는 이미 안정적이다.** p99 328ms로 카카오 기준 3,000ms의 11%다. 지연의 **78%가
슬롯 2·3을 채우는 비용**이다.

반환 개수별로 보면 원인이 분명하다.

| 반환 | 곳 수 | 평균 |
|---|---|---|
| 3개 | 45 | **220ms** |
| 2개 | 7 | 513ms |
| 1개 | 4 | 420ms |
| 0개 | 4 | 371ms (p99 1,395ms) |

`_standard_alternatives()`가 `route_variant`를 `2,4,6,1,3,5,7` 순서로 **순차** 시도한다.
3개가 금방 모이면 세 번에 끝나고, 안 모이면 일곱 번을 다 돌며 예산을 태운다. 최악은
수서역 1,395ms로, 0개를 반환하면서 일곱 개를 전부 시도했다.

**도로망 밀도는 예측 변수가 아니다.** 2km 내 노드 수로 3분위를 나눠도 227~349ms로 차이가
없다. 밀도 기반 사전 필터링은 근거가 없으므로 하지 않는다.

### 3단 구조

슬롯을 서로 다른 비용의 재료로 채운다.

```text
1번  요청 위치에서 생성            61ms   항상 조건 충족
2·3번 2km 내 프리셋 중 조건 통과     0ms   있으면 즉시
모자라면 병렬 variant로 채움        +60ms  나머지
```

### 프리셋으로 채울 수 있는 범위

프리셋은 각 역에서 동물 모양이 완성되는 최소 거리로 만들어져 거리 분포가 치우쳐 있다.
중앙값 8.7km이고 5.5km 이하는 339개 중 34개뿐이다. 따라서 요청 거리에 따라 커버리지가 갈린다.

| 조건 | 2·3번 채움 | 중앙값 |
|---|---|---|
| 2km 내 · 거리 미지정 | **48/60** | 6개 |
| 2km 내 · 10km ±10% | 45/60 | 4개 |
| 2km 내 · 5km ±10% | **20/60** | 1개 |
| 5km 내 · 5km ±10% | 46/60 | 5개 |

- 거리를 말하지 않은 요청과 10km 근처 요청은 프리셋이 대부분 채운다.
- `"5km"` 같은 짧은 거리는 프리셋이 못 채우므로 병렬 variant가 받는다.
- **반경은 2km로 고정한다.** 5km까지 넓히면 커버리지는 오르지만 5km 떨어진 출발지는
  "근처"가 아니다. 결정 1·2에서 임의 위치를 거부한 이유와 충돌한다.
- **거리 조건은 절대 완화하지 않는다.** §5의 "조건을 어긴 대체 코스를 성공 카드로 반환하지
  않는다"가 그대로 적용된다. 프리셋으로 못 채우면 채우지 않는다.

### 구현은 한 줄이 막고 있다

```python
# server.py:684
animals = _any_animal_matches(preset_probe, PRESET_SEARCH_RADIUS_M) if shape != "standard" else []
```

동물 요청에는 이미 프리셋으로 슬롯을 채우고 있고, 일반 코스에서만 `else []`로 꺼져 있다.
이 가드를 풀고 반경을 `PRESET_SEARCH_RADIUS_M`(30km, 사실상 서울 전역) 대신 2km로 좁힌다.

**일반 코스 요청에 동물 코스가 대안으로 섞인다.** 위젯이 `"고래 모양"` / `"일반 러닝"`으로
라벨을 붙이고 `course_selection.primary_matches_requested_shape`가 이미 이 사실을 표현하므로
사용자와 모델 모두 무엇을 받았는지 알 수 있다. 1번은 항상 요청한 종류다.

### 병렬 생성

`_offload_map()`이 이미 병렬 헬퍼로 존재한다. 주석에 "동물 서베이가 네 동물을 동시에
생성하도록"이라고 적혀 있다. `_standard_alternatives()`만 순차 루프다.

기본 + variant `2,4,6`을 한 번에 던지도록 바꿔 측정했다(n=50).

| | 평균 | p95 | p99 | 3개 확보 |
|---|---|---|---|---|
| 현재 순차 | 162ms | 386ms | 543ms | 22/50 |
| **병렬** | **122ms** | **238ms** | **347ms** | **27/50** |
| 변화 | −25% | −38% | −36% | +5곳 |

빨라지면서 코스도 더 많이 찾는다. 순차는 실패한 variant에 예산을 하나씩 태우지만 병렬은
동시에 던지고 돌아온 것을 쓴다.

### 0개 반환 조기 종료

기본 코스조차 만들지 못하는 출발지는 variant를 일곱 개 돌 이유가 없다. 1번 생성이 실패하면
즉시 `insufficient_courses`로 끝낸다. 수서역 사례가 1,395ms에서 약 330ms로 줄어든다.

### `RUNART_POOL_WORKERS`는 2로 유지한다

두 가이드 어디에도 프로세스 수·메모리·CPU 조항이 없으므로 4로 올리는 것은 **정책 위반이
아니다.** 그러나 실측 결과 권하지 않는다.

| 설정 | 부모 | 워커 | 총 RSS |
|---|---|---|---|
| `2` (현재) | 514MB | 594 + 576MB | **1.7GB** |
| `4` | 438MB | 572 + 588 + 588 + 554MB | **2.7GB** |

워커당 약 580MB다. `spawn` 프로세스라 각자 그래프와 시설·인프라 데이터를 따로 로드한다.
2 → 4는 **+1.1GB**인데 얻는 것은 병렬 단계에서 127ms → 107ms, 즉 16%뿐이다.

개발가이드 5.1.b는 "MCP서버에 심각한 문제가 발생한 경우 … Kakao Tools에서 해당 MCP를 삭제
처리. 모든 사용자 도구함에서도 제거"라고 규정한다. PlayMCP in KC 컨테이너의 메모리 한도를
확인하지 않은 상태에서 1.1GB를 더 쓰는 것은 16% 지연 개선의 대가로 서비스 삭제 위험을
사는 일이다.

병렬화의 이득(p99 543 → 347ms)은 워커 수와 무관하게 얻어진다. 올리려면 다음이 먼저다.

- 배포 컨테이너의 메모리 한도 확인
- 워커 4개 기동 상태에서 실제 RSS 관측
- 한도의 70% 이하일 때만 상향

코드 변경이 아니라 환경변수 하나이므로 배포 후에도 바꿀 수 있다.

### 테스트

- 1번 코스가 항상 요청한 출발지·종류·조건을 만족한다
- 2·3번 프리셋이 요청 거리 ±10%를 벗어나면 채우지 않는다
- 2·3번 프리셋이 출발지에서 2km를 넘으면 채우지 않는다
- 1번 생성이 실패하면 variant를 시도하지 않고 `insufficient_courses`
- 병렬 경로가 프로세스 풀 없이도(폴백) 동작한다
- 일반 코스 요청에 동물 대안이 섞여도 `primary_matches_requested_shape`가 참이다

## 배포·롤백 게이트

### 배포 전 차단 조건

- 배포 대상이 커밋으로 고정되지 않은 상태
- `/healthz.ready != true`
- 이미지의 `release_sha`가 배포 커밋과 다름
- 적용된 툴 설명이 새 계약과 다름
- 통합 툴 description이 1,024자를 넘음
- 25개 구 분류 테스트 실패
- 2·3번 슬롯 프리셋이 요청 거리 ±10% 또는 2km 반경을 벗어남
- `"서울 시내"`가 지오코딩되는 회귀
- 무출발지 공원 추천 회귀 테스트 실패
- 야간 동물이 프리셋을 재사용하고 있음
- 편집 안내가 위젯 화면에 보이지 않음
- 코스 부재 실패가 여전히 `invalid_request`로 나감
- Preview 필수 발화 중 하나라도 실패
- 이전 이미지 SHA와 툴 스키마 복구 절차가 준비되지 않음

### 배포 절차

1. 새 이미지에 Git SHA 삽입
2. 별도 스테이징 endpoint에서 `/healthz` 확인
3. MCP Inspector로 툴 개수·스키마·직접 호출 확인
4. PlayMCP에서 적용 대상 9개 툴 재등록·새로고침
5. Kakao Tools Preview에서 위 표의 발화 테스트. "새 대화 시작"으로 진행하고, 호출률을 위해 "Kakao Tools 버튼"을 누른 채 발화한다
6. 성공 응답의 `release_sha`, 범위, 후보 수 기록
7. 그 뒤에만 운영 endpoint로 승격

Preview는 실제 ChatGPT 환경이라 툴 호출이 100% 보장되지 않는다. 특정 툴 호출이 필요하면
`"create_seoul_running_course 툴을 사용해서 답변해줘"`처럼 이름을 지정한다.

### 관측 로그

새 로깅 시스템은 넣지 않고 기존 로그에 다음 구조 필드만 추가한다.

- `release_sha`
- `start_scope`
- `district`
- `candidate_count`
- `eligible_count`
- 조건별 `rejection_counts`
- `result_code`
- `duration_ms`

상호명·주소 원문은 개인정보와 불필요한 위치 노출을 피하기 위해 기록하지 않는다. 구 이름은
25개 값 중 하나이므로 개인 식별에 쓰이지 않는다.

**`missing_start` 비율을 반드시 본다.** 결정 1·2가 사용자에게 얼마나 자주 되묻게 하는지가
이 지표다. 되묻는 비율이 높은데 다음 턴 전환율이 낮다면 정책을 재검토할 근거가 된다.

### 롤백

데이터베이스 변경이 없으므로 전체 이미지 롤백이 가장 단순하다.

1. 직전 운영 이미지 SHA 보존
2. 오류 발생 시 endpoint를 직전 이미지로 복귀
3. PlayMCP 툴 설명도 직전 버전으로 재적용
4. `/healthz.release_sha` 확인
5. Preview에서 특정 출발지·구·공원 최소 스모크 테스트
